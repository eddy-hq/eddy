# Native iOS is a thin shell; push is APNs

The native iOS app is a shell, not a second client. A `WKWebView` loads the existing PWA from the household's Eddy domain and renders every screen — feed, player, request landing, profile, search. Swift owns only the things a web page cannot do on iOS: a share extension (replacing the Shortcut request flow), an App Intent so Shortcuts and Siri can still reach Eddy, APNs push notifications (lock-screen actions to follow), `eddy://` deep links, a "Tailscale not connected" fallback screen, and the user identity currently passed around as a `?userId=` query parameter, held in the Keychain instead. There is no native feed, no native player, no second design system.

The shape is the decision. A fully native UI would double every subsequent UI phase — Drift, overrides, the guard review surface would each have to be built twice, and the PWA would still exist because other devices still use the web app. The shell buys the four things that are genuinely missing (a real share sheet target, real push, a real app icon, an identity that survives a dropped query param) and buys nothing else. When a later phase changes the feed, the shell changes not at all.

**APNs is the first real transport behind `notify()`.** ntfy came out of the codebase on 2026-09-19 ([[0003-one-notification-channel]], amendment), so there is no migration to stage and no dual delivery to guard against: the notifications module logs every event today, and APNs is what it will send with. [[0003-one-notification-channel]]'s rule is one channel, not one technology, and this is the technology. Nothing outside the module changes: the call sites keep calling `notify(event, recipient)`, and future action buttons will hit signed-token URLs under the requirement below.

**Push no longer waits for Phase 6; Phase 6 waits for push.** With the transport log-only, three of the five notification kinds — `circuit_open`, `download_failure_streak`, `download_alert` — are ops alerts to the parent that nobody now receives, and a pipeline that has gone dark announces it to a log file. That is a live gap, not a future one, so the push stages follow the distribution stage directly instead of waiting on the guard. The dependency now runs the other way: Phase 6 (guard live) cannot ship without a push channel, because an uncertain verdict has to reach a parent to be adjudicated.

**Payloads that transit Apple carry an opaque message id and generic placeholder copy, and nothing else** — no title, no channel name, no kid name, no request detail. The id is random and stored against the message; it is never a request id, a YouTube id, or anything else that means something off the home server. A Notification Service Extension wakes on delivery, fetches the real content from the home server over the private network — authenticated as the device's own user, so one household member's device can't read another's notifications — and rewrites the notification in place; if the fetch fails it shows generic copy ("Something new in Eddy") and the content is only ever seen once the app is opened. This is [[0004-kids-consumption-stays-home]] applied to the push path: an opaque id goes out, the content is fetched back. Whether a service extension can reliably reach a tailnet-only host while the VPN is backgrounded is the one genuinely unproven assumption here, and it is tested on a real device in the final build stage before the household is asked to rely on it.

**Distribution is ad hoc, not TestFlight.** TestFlight's tester rules don't fit a family's own devices — so the app is signed with ad hoc provisioning against registered device UDIDs, with an OTA install manifest served from the Eddy domain behind the home server's reverse proxy (tailnet-only, like everything else). The cost is a 12-month cliff: the profile expires, the app stops launching, and every device must be re-signed yearly. The watchdog warns a month out. Each self-hosting household signs with its own Apple Developer account, which is the same shape as everything else in Eddy.

**Links are `eddy://` only.** Universal links would require Apple to fetch `apple-app-site-association` from the public internet; the Eddy domain resolves tailnet-only by design, so they cannot work without exposing the host. Paths under the custom scheme stay identical to the web paths — `eddy://feed`, `eddy://watch/{id}` — so a link is a protocol-prefix change, not a route rewrite.

## Consequences

- **`notify()`'s real signature is `notify(event, recipient)`** — event-first, payload folded into the event union — not the `notify(user_id, event, payload)` documented in brief §12. The APNs sender goes inside `createNotifications`, so the divergence stays contained, but §12's code block is wrong; the note under it now records the real signature and marks the code canonical.
- **The `devices` table exists and is completely unused** — no code reads or writes `device_id`. It becomes the home for APNs tokens: a token column, a `last_seen_at`, and a registration endpoint. It is not a new table, but it is a first use.
- **The signed-token payload still needs a target id and an action route before a lock-screen action can work.** `generateActionToken(handler, userId)` signs `handler:userId:expires` only — no target — and no `/action/{handler}` route is mounted. Both are owed before the first action button ships; see the requirement below.
- **The shell loads the PWA over HTTPS from the Eddy domain; it never serves local HTML.** Every PWA fetch is origin-relative and leans on the server's SPA fallback. Bundling the web assets into the app would break all of them and force an explicit API base plus CORS the server does not send.
- **`navigator.share` disappears in `WKWebView`** unless the shell supplies a bridge. The share tile is already `canShare`-gated and hides itself, so the degradation is graceful, but the tile is a follow-up to the shell stage.
- **Until this ships, nobody is notified of anything.** A user whose device registration or service extension misbehaves falls back to the log, which is the same place everyone is today — so the rollout order is a convenience, not a safety property. Device-test before trusting it; there is no second channel underneath.
- **A yearly operational chore.** Profile re-signing, UDID registration for any new device, and an Apple Developer account per household. This supersedes the earlier "TestFlight only, permanent" intention.

## Requirement: lock-screen actions (absorbs 0005)

[[0005-single-use-signed-tokens]] is folded in here, because notification actions only exist through this shell. When lock-screen actions are built, every action is a signed, single-use URL, the same whatever channel renders the button. The token carries the user, the action and the target, and the server marks it used in the same step that checks it, so a second tap, a screenshot or a replay within the hour resolves to a refusal. A parent who genuinely needs to act twice gets a fresh notification, not a reusable link. Used tokens must be pruned on a schedule, which nothing does yet. None of the action side is built yet; the single-use token itself is, and device invites already rely on it ([[0016-the-acting-user-comes-from-a-device-credential]]).

## Considered and rejected

- **Fully native SwiftUI UI.** Doubles every later UI phase and creates a second design system to keep in sync, for screens the household already has working on its other devices. The four native capabilities are what's missing, not the rendering.
- **React Native / Capacitor / a cross-platform wrapper.** The household is iOS-only (§18), so the portability is worth nothing here, and each adds a build toolchain and a dependency tree to keep alive for a share extension and a push handler.
- **TestFlight.** Cleaner distribution and automatic expiry handling, but its tester rules don't fit a family's own devices. Non-starter.
- **A narrow shell with no `WKWebView`** — notifications and share extension only, with everything else still opened in Safari. Loses the app icon, the identity in the Keychain, and the deep-link target; the share extension would still have to hand off to Safari to show a result.
- **Plain APNs payloads with real titles.** Simpler and more reliable than a service extension, and it would put kid request titles and creator names through Apple's servers. Rejected on [[0004-kids-consumption-stays-home]]; the generic-copy fallback is the price.
- **Universal links.** Require a publicly fetchable `apple-app-site-association`. The Eddy domain is tailnet-only and stays that way.

## Amended — 2026-10-09: push shipped

Push shipped (#203) and works on the household's iOS devices; lock-screen actions have not followed yet. The privacy design held as written: Apple carries placeholder copy and an opaque id, and the service extension fetches the content from the home server, readable only by its recipient. An unknown id, someone else's id and an expired id all return the same 404, so the endpoint reveals nothing about which messages exist, and messages expire after 24 hours. Two consequences above have aged. The `devices` table is now in use, for APNs tokens and, since [[0016-the-acting-user-comes-from-a-device-credential]], for the device credential. And "until this ships, nobody is notified" no longer applies: a device whose registration fails still falls back to the log.
