# Native iOS is a thin shell; APNs replaces ntfy

The native iOS app is a shell, not a second client. A `WKWebView` loads the existing PWA at `https://eddyhq.app` and renders every screen — feed, player, request landing, profile, search. Swift owns only the things a web page cannot do on iOS: a share extension (replacing the Shortcut request flow), an App Intent so Shortcuts and Siri can still reach Eddy, APNs push with lock-screen action buttons, `eddy://` deep links, a "Tailscale not connected" fallback screen, and the user identity currently passed around as a `?userId=` query parameter, held in the Keychain instead. There is no native feed, no native player, no second design system.

The shape is the decision. A fully native UI would double every subsequent UI phase — Drift, overrides, the guard review surface would each have to be built twice, and the PWA would still exist because the iPads and the Mac use it. The shell buys the four things that are genuinely missing (a real share sheet target, real push, a real app icon, an identity that survives a dropped query param) and buys nothing else. When a later phase changes the feed, the shell changes not at all.

**APNs replaces ntfy, per user, inside `notify()`.** [[0003-one-notification-channel]]'s rule is one channel, not one technology, and it anticipated this swap — so the switch is a per-user branch inside the notifications module, never dual delivery. A user is on ntfy or on APNs; as each household member's device registers and the channel is proven, their ntfy topic is retired. Steve first, then the boys. The branch is migration scaffolding with an end state, not a permanent capability: once the last user has moved, the ntfy transport and its config come out of the codebase. Replace, not augment. Nothing outside the module changes: the eight call sites keep calling `notify(event, recipient)`, and action buttons keep hitting the same signed-token URLs ([[0005-single-use-signed-tokens]]).

**Payloads that transit Apple carry an opaque message id and generic placeholder copy, and nothing else** — no title, no channel name, no kid name, no request detail. The id is random and stored against the message; it is never a request id, a YouTube id, or anything else that means something off the M4. A Notification Service Extension wakes on delivery, fetches the real content from the M4 over Tailscale — authenticated as the device's own user, so one household member's device can't read another's notifications — and rewrites the notification in place; if the fetch fails it shows generic copy ("Something new in Eddy") and the content is only ever seen once the app is opened. This is [[0004-kids-consumption-never-leaves-m4]] applied to the push path, and it is deliberately the same trick ntfy's iOS delivery already plays (poll-request forwarding: id out, content fetched back). Whether a service extension can reliably reach a tailnet-only host while the VPN is backgrounded is the one genuinely unproven assumption here, and it is tested on a real device in stage 4 before any user is cut over.

**Distribution is ad hoc, not TestFlight.** TestFlight requires testers to be 13 or older, which excludes Boy2 — so the app is signed with ad hoc provisioning against registered device UDIDs, with an OTA install manifest served from `eddyhq.app` behind Caddy (tailnet-only, like everything else). The cost is a 12-month cliff: the profile expires, the app stops launching, and every device must be re-signed yearly. The watchdog warns a month out. Each self-hosting household signs with its own Apple Developer account, which is the same shape as everything else in Eddy.

**Links are `eddy://` only.** Universal links would require Apple to fetch `apple-app-site-association` from the public internet; `eddyhq.app` resolves tailnet-only by design, so they cannot work without exposing the host. Paths under the custom scheme stay identical to the web paths — `eddy://feed`, `eddy://watch/{id}` — so a link is a protocol-prefix change, not a route rewrite.

## Consequences

- **`notify()`'s real signature is `notify(event, recipient)`** — event-first, payload folded into the event union — not the `notify(user_id, event, payload)` documented in brief §12. The APNs branch goes inside `createNotifications`, so the divergence stays contained, but §12's code block is wrong; the note under it now records the real signature and marks the code canonical.
- **The `devices` table exists and is completely unused** — no code reads or writes `device_id`. It becomes the home for APNs tokens: a token column, a `last_seen_at`, and a registration endpoint. It is not a new table, but it is a first use.
- **The signed-token payload has to gain a target id before an APNs action button can work.** `generateActionToken(handler, userId)` today signs `handler:userId:expires` only — no target — which contradicts [[0005-single-use-signed-tokens]]'s "carrying the user, the action, and the target ID". No `/action/{handler}` route is mounted either. Both are owed by Phase 6 regardless of the shell; APNs makes them visible sooner because the buttons render on the lock screen.
- **The shell loads the PWA over HTTPS from `eddyhq.app`; it never serves local HTML.** Every PWA fetch is origin-relative and leans on the server's SPA fallback. Bundling the web assets into the app would break all of them and force an explicit API base plus CORS the server does not send.
- **`navigator.share` disappears in `WKWebView`** unless the shell supplies a bridge. The share tile is already `canShare`-gated and hides itself, so the degradation is graceful, but the tile is a stage-2 follow-up.
- **The ntfy→APNs cutover is per user and reversible per user** — a user whose device registration or service extension misbehaves goes back to their ntfy topic by flipping one row. Topics are retired only once APNs is proven for that person.
- **A yearly operational chore that ntfy never had.** Profile re-signing, UDID registration for any new device, and an Apple Developer account per household. This supersedes the earlier "TestFlight only, permanent" intention.

## Considered and rejected

- **Fully native SwiftUI UI.** Doubles every later UI phase and creates a second design system to keep in sync, for screens the household already has working on iPad and Mac. The four native capabilities are what's missing, not the rendering.
- **React Native / Capacitor / a cross-platform wrapper.** The household is iOS-only (§18), so the portability is worth nothing here, and each adds a build toolchain and a dependency tree to keep alive for a share extension and a push handler.
- **TestFlight.** Cleaner distribution and automatic expiry handling, but its 13+ age floor excludes a user. Non-starter.
- **A narrow shell with no `WKWebView`** — notifications and share extension only, with everything else still opened in Safari. Loses the app icon, the identity in the Keychain, and the deep-link target; the share extension would still have to hand off to Safari to show a result.
- **Plain APNs payloads with real titles.** Simpler and more reliable than a service extension, and it would put kid request titles and creator names through Apple's servers. Rejected on [[0004-kids-consumption-never-leaves-m4]]; the generic-copy fallback is the price.
- **Universal links.** Require a publicly fetchable `apple-app-site-association`. `eddyhq.app` is tailnet-only and stays that way.
